1. Was macht die Anwendung?

Die Website zeigt eine Liste von rund 4.000 Pflege- und Beratungsstellen in Deutschland. Man kann die Liste durchsuchen (Name, Ort, PLZ), nach Bundesland und Angebotsart filtern und beliebig viele Stellen per Checkbox auswählen. Ein Klick auf „E-Mail an Auswahl senden“ öffnet das eigene Mailprogramm (Outlook, Apple Mail …) mit allen gewählten Adressen bereits eingetragen.

Warum öffnet sich das eigene Mailprogramm statt dass der Server die Mail verschickt? Weil der Server dann keine Mail-Zugangsdaten braucht, keine E-Mails speichert und nicht als Spam-Schleuder missbraucht werden kann. Technisch ist das ein ganz normaler mailto:-Link – wie ein Link, der aber nicht eine Seite, sondern das Mailprogramm öffnet.

Außerdem gibt es eine Login-Pflicht: Niemand sieht die Liste, ohne sich vorher angemeldet zu haben.

2. Die Bausteine im Überblick

Die Anwendung besteht aus mehreren Programmen, die zusammenarbeiten. Jedes läuft in einem eigenen Container (siehe Glossar) auf ein und demselben Server:

Internet (Browser der Nutzer:innen) │ verschlüsselt (https, Port 443) ▼ ┌─────────────────────────────────────────────────────────┐ │ Ubuntu-Server │ │ │ │ ┌───────────┐ ┌──────────────────────────┐ │ │ │ nginx │ ───────► │ App (FastAPI / Python) │ │ │ │ "Türsteher"│ │ + Datenbank im RAM │ │ │ └───────────┘ └──────────────────────────┘ │ │ │ │ │ │ /idp/… ┌──────────────┐ ┌──────────┐ │ │ └──────────────► │ Keycloak │─►│ Postgres │ │ │ │ (Login) │ │ (für KC) │ │ │ └──────────────┘ └──────────┘ │ │ │ │ internes Docker-Netzwerk – von außen nicht erreichbar │ └─────────────────────────────────────────────────────────┘
BausteinWas er tutWarum genau dieser?
nginx Der einzige Baustein, der aus dem Internet erreichbar ist. Entschlüsselt HTTPS, leitet Anfragen an die App bzw. an Keycloak weiter, bremst zu viele Anfragen pro Sekunde aus (Rate-Limiting). Weltweit bewährter Standard-„Türsteher“. Alles Sicherheitsrelevante an der Außengrenze passiert an genau einer Stelle.
App (Python, FastAPI) Liefert die Webseite aus und beantwortet die Datenabfragen (/api/centers). Lädt beim Start die CSV-Datei in eine kleine Datenbank im Arbeitsspeicher. Python ist einsteigerfreundlich; FastAPI ist klein, schnell und erzeugt die API-Dokumentation automatisch (/api/docs).
Keycloak Übernimmt den kompletten Login: Benutzerkonten, Passwörter, Passwort-vergessen, Schutz vor Rate-Angriffen. Login selbst zu programmieren ist fehleranfällig. Keycloak ist eine Open-Source-Standardlösung, die genau das seit Jahren macht.
Postgres (nur für Keycloak) Speichert Keycloaks Benutzerkonten dauerhaft auf der Festplatte. Ohne echte Datenbank würde Keycloak alle Konten bei jedem Neustart vergessen.
Warum liegt die Datenbank der App „nur im Arbeitsspeicher“? Die Stellen-Daten ändern sich nicht durch die Nutzer:innen. Die CSV-Datei im Repository ist die „Wahrheit“; beim Start wird sie in eine SQLite-Datenbank im RAM geladen. Vorteil: kein Datenbank-Server nötig, trotzdem echtes SQL zum Filtern/Suchen. Startet der Container neu, wird einfach alles frisch geladen – es kann nichts verloren gehen.

3. Was passiert bei einem Seitenaufruf?

  1. Du tippst https://pflege-finder.example.org ein. Die Anfrage landet bei nginx, der die Verschlüsselung aufmacht.
  2. nginx reicht die Anfrage intern an die App weiter.
  3. Die App prüft: Bist du eingeloggt? (Dafür schaut sie in ein signiertes Cookie.) Falls nein → Weiterleitung zu /auth/login → weiter zu Keycloak.
  4. Du meldest dich bei Keycloak an. Keycloak schickt dich mit einem Einmal-Code zurück zur App (/auth/callback).
  5. Die App tauscht diesen Code direkt (Server zu Server, im internen Netz) gegen deine Benutzerinfos ein und merkt sich „eingeloggt“ im Cookie.
  6. Jetzt bekommst du die Seite. Das JavaScript im Browser lädt die Liste über /api/centers?… nach, du filterst, wählst aus, klickst auf „E-Mail senden“ → mailto: öffnet dein Mailprogramm.
Warum zwei verschiedene Adressen für Keycloak (OIDC_ISSUER und OIDC_ISSUER_INTERNAL)? Dein Browser erreicht Keycloak nur über die öffentliche Adresse (https://…/idp/). Die App dagegen spricht mit Keycloak direkt im Container-Netz (http://keycloak:8080/…) – schneller und ohne Umweg über nginx. Beides zeigt auf dasselbe Keycloak, nur über unterschiedliche „Türen“.

5. Sicherheit – einfach erklärt

HTTPS

Alles zwischen Browser und Server ist verschlüsselt. Unverschlüsselte Aufrufe (http://) werden automatisch auf https:// umgeleitet.

Login über Keycloak – „sicher von Haus aus“

Die Login-Pflicht ist standardmäßig an. Fehlen die Keycloak-Zugangsdaten, startet die App absichtlich gar nicht („Fail-fast“) – lieber ein sichtbarer Fehler als eine versehentlich offene Website.

Sicherheits-Header

Jede Antwort enthält Anweisungen an den Browser, z. B. „führe nur Skripte von dieser Seite aus“ (Content-Security-Policy) oder „zeige mich nicht in fremden Frames an“. Das schützt vor eingeschleustem Fremdcode.

Container-Härtung

  • Die App läuft nicht als Administrator (non-root) im Container.
  • Das Dateisystem ist schreibgeschützt; nur /tmp ist beschreibbar.
  • CPU und RAM sind begrenzt – ein Fehler kann nicht den ganzen Server lahmlegen.
  • Nur nginx hat offene Ports nach außen; App und Keycloak sind nur intern erreichbar.

Rate-Limiting & Begrenzung

nginx erlaubt pro IP nur ~10 Anfragen/Sekunde; die API liefert maximal 500 Einträge pro Anfrage. Niemand kann die ganze Adressliste „auf einen Schlag“ absaugen.

Keine Geheimnisse im Code

Passwörter und Schlüssel stehen ausschließlich in der lokalen .env-Datei, die per .gitignore vom Repository ausgeschlossen ist.

6. Die letzten Verbesserungen – was, wie, warum

Nach einer kritischen Bewertung des Repositories wurden folgende Punkte umgesetzt. Legende: Sicherheit Korrektur Neu

6.1 Platzhalter-Passwörter werden erkannt Sicherheit

Problem: Die Vorlage .env.example enthielt SECRET_KEY=change-me. Die App prüfte aber nur auf einen anderen Standardwert. Wer die Vorlage einfach kopierte, lief produktiv mit einem erratbaren Schlüssel – damit könnte man Login-Cookies fälschen.

Lösung: In app/config.py gibt es jetzt eine Liste bekannter Platzhalter und eine Mindestlänge von 32 Zeichen. Im Produktivmodus verweigert die App den Start, wenn der Schlüssel schwach ist. Auch ein Platzhalter als OIDC_CLIENT_SECRET gilt als „nicht konfiguriert“.

PLACEHOLDER_VALUES = {"", "change-me", "insecure-dev-secret-change-me"}
MIN_SECRET_KEY_LENGTH = 32

@property
def secret_key_is_weak(self) -> bool:
    return is_placeholder(self.secret_key) or len(self.secret_key) < 32

6.2 Keycloak produktionsreif Sicherheit Korrektur

Problem: Keycloak lief im Entwicklungsmodus (start-dev) mit einer Spielzeug-Datenbank im RAM – jeder Neustart löschte alle Benutzer. Hostname und erlaubte Rücksprung-Adressen waren fest auf localhost verdrahtet, und genau diese Konfiguration wurde automatisch auf den echten Server ausgerollt.

Lösung in docker-compose.yml:

  • Eigener Postgres-Container mit dauerhaftem Speicher (Volume) für Keycloak.
  • start statt start-dev (umschaltbar per KC_COMMAND für lokal).
  • Hostname und App-Adresse kommen aus .env (KC_HOSTNAME, APP_PUBLIC_URL). In keycloak/realm-export.json steht nur noch ${APP_PUBLIC_URL}/auth/callback – Keycloak setzt den Wert beim Import selbst ein. Keine localhost-Einträge mehr auf dem Server.
  • Veraltetes KC_PROXY=edge durch das aktuelle KC_PROXY_HEADERS=xforwarded ersetzt; Image-Version exakt gepinnt.
Warum Umgebungsvariablen statt fester Werte? Derselbe Code soll lokal (https://localhost) und auf dem Server (https://pflege-finder.example.org) laufen. Alles, was sich zwischen den Umgebungen unterscheidet, gehört in die .env, nicht in den Code.

6.3 Automatische Tests und Lint als „Schranke“ Neu

Problem: Jeder Push auf main ging sofort und ungeprüft auf den Server – ein Tippfehler hätte die Seite lahmgelegt.

Lösung: Ein Ordner tests/ mit 17 Pytest-Tests (API-Filter, Seitengröße, Login-Umleitung, Fail-fast-Checks) und der Code-Prüfer ruff. Beides läuft jetzt als eigener Job vor dem Bauen – und auch für Pull Requests. Schlägt ein Test fehl, wird nichts deployt.

# .github/workflows/deploy.yml (Auszug)
jobs:
  test:                      # 1) Prüfen
    steps:
      - run: ruff check .
      - run: pytest -q
  build-and-push:            # 2) Nur wenn Tests grün
    needs: test
  deploy:                    # 3) Nur wenn Build ok
    needs: build-and-push
Wie funktionieren die Tests ohne echten Server?

FastAPI bringt einen TestClient mit, der die App direkt im Speicher aufruft – kein Docker, keine Netzwerkverbindung. Die Tests setzen Umgebungsvariablen (z. B. AUTH_ENABLED=false oder eine kleine Test-CSV mit 3 Einträgen), laden die App neu und prüfen die Antworten. Ein Test kontrolliert z. B., dass die App mit SECRET_KEY=change-me im Produktivmodus nicht startet.

6.4 Nachvollziehbare Deployments statt „latest“ Korrektur

Problem: Der Server zog immer das Image mit dem Tag latest. Man wusste nie genau, welche Version läuft, und ein Zurückrollen war schwierig.

Lösung: Jeder Build wird zusätzlich mit dem Kürzel des Git-Commits getaggt (z. B. sha-1a2b3c4). Der Deploy-Schritt schreibt diesen Tag als IMAGE_TAG in die Server-.env. Rollback = alten Tag eintragen, docker compose up -d.

6.5 Stabile IDs für die Stellen Korrektur

Problem: Die ID einer Stelle war einfach ihre Zeilennummer in der CSV. Sortiert jemand die Datei um, bekommen alle Stellen neue IDs – Links und Auswahlen zeigen plötzlich auf andere Einträge.

Lösung: app/seed.py übernimmt jetzt die Spalte unsere_id aus der CSV als Primärschlüssel. Außerdem leert der Import die Tabelle vorher, damit er beliebig oft wiederholt werden kann (wichtig für Tests).

6.6 Kleinere Code-Korrekturen in der API Korrektur

  • Ungültiger Filter wird abgelehnt: ?angebot=foo wurde bisher stillschweigend ignoriert. Jetzt ist der Parameter als feste Auswahlliste (Literal) definiert → Antwort 422 mit Fehlermeldung, und die erlaubten Werte erscheinen automatisch in der API-Doku.
  • Suche nach % oder _: Diese Zeichen sind in SQL Platzhalter („beliebig viele Zeichen“). Sie werden jetzt maskiert, sodass wirklich nach dem Zeichen gesucht wird.
  • Zählen statt alles laden: Für „x von y Treffern“ wurden bisher alle Treffer aus der Datenbank geholt und dann gezählt. Jetzt zählt die Datenbank selbst (COUNT(*)) – schneller und weniger Speicher.

6.7 Strengere Sicherheits-Header Sicherheit

Die Content-Security-Policy erlaubte „inline“-CSS, obwohl keines verwendet wird. Die Ausnahme wurde entfernt und frame-ancestors 'none' ergänzt (moderne Form von „nicht in fremde Seiten einbetten“).

6.8 nginx: moderne TLS-Einstellungen Sicherheit

Die Verschlüsselungsverfahren folgen jetzt der empfohlenen „Mozilla Intermediate“-Liste; TLS-Sitzungen werden zwischengespeichert (schnellere Folgeaufrufe). Für den Keycloak-Pfad /idp/ wurde das Rate-Limit gelockert, weil die Admin-Oberfläche viele Dateien auf einmal lädt und sonst ausgebremst wurde.

6.9 Aufgeräumt Korrektur

  • Testdateien (Test.txt, Test123.txt) und eine 9 MB große Kopie der Daten (pflegestellen.json, Root-pflegestellen.csv) entfernt. Es gibt jetzt genau eine Datenquelle: app/data/pflegestellen.csv.
  • Veraltete Python-Importe ersetzt (uvicorn-worker-Paket), doppelter Healthcheck entfernt.
  • Kommentare und README/ROADMAP, die noch „Login kommt später“ sagten, aktualisiert.
  • Dependabot eingerichtet: GitHub schlägt automatisch Updates für Python-Pakete, Docker-Images und Actions vor.
Noch offen (bewusst nicht umgesetzt) Demo-Benutzer demo auf dem Server löschen · Impressum & Datenschutzerklärung · Rollen/Rechte (aktuell darf jeder Eingeloggte alles) · GitHub-Actions auf feste Commit-Versionen pinnen. Alles in docs/ROADMAP.md vermerkt.

7. Vom Code zum laufenden Server

Wird Code in den Branch main gemerged, passiert vollautomatisch:

git push main │ ▼ [1] test ──────── ruff + pytest ✗ Fehler? → Stopp, nichts passiert │ ✓ ▼ [2] build-and-push ── Docker-Image bauen, nach GHCR hochladen │ (Tags: latest + sha-<commit>) ▼ [3] deploy ────── per SSH auf den Server: git pull · IMAGE_TAG in .env schreiben · docker compose pull & up -d │ ▼ [4] health check ─ 12× https://localhost/healthz abfragen ✗ nach 60 s nicht gesund? → Logs ausgeben, Job rot
Warum ein fertiges Image statt auf dem Server zu bauen? Das Image wird einmal gebaut und getestet; der Server führt exakt dieses aus. So laufen lokal, in CI und produktiv garantiert dieselben Bytes.

pip install -r app/requirements.txt -r requirements-dev.txt

9. Glossar

API
Eine Schnittstelle, über die Programme (hier: das JavaScript im Browser) Daten abfragen – statt einer fertigen Webseite kommt rohes JSON zurück.
Container / Docker
Ein Container ist ein abgeschottetes Mini-System, in dem genau ein Programm mit allem läuft, was es braucht. Docker baut und startet diese Container. Docker Compose beschreibt mehrere Container und ihr gemeinsames Netzwerk in einer Datei.
CI/CD
„Continuous Integration / Continuous Deployment“: Code wird bei jeder Änderung automatisch geprüft (CI) und ausgerollt (CD). Hier über GitHub Actions.
Cookie (Session)
Kleines Datenpaket, das der Browser bei jeder Anfrage mitschickt. Die App speichert darin „eingeloggt als …“ – signiert mit dem SECRET_KEY, damit es niemand fälschen kann.
CSV
Einfache Textdatei mit Tabellendaten, Spalten durch ; getrennt.
Fail-fast
Prinzip: Bei fehlerhafter Konfiguration sofort und sichtbar abbrechen, statt „irgendwie“ weiterzulaufen.
HTTPS / TLS
Verschlüsselte Verbindung zwischen Browser und Server (das Schloss-Symbol).
Lint (ruff)
Automatische Code-Prüfung auf Stil- und häufige Logikfehler, noch bevor etwas läuft.
Middleware
Code, der vor jeder Anfrage läuft – wie ein Türsteher, der prüft, ob du rein darfst, bevor die eigentliche Seite angefasst wird.
OIDC (OpenID Connect)
Standardverfahren für „Login über einen anderen Dienst“ – dasselbe Prinzip wie „Mit Google anmelden“, nur mit Keycloak.
Rate-Limiting
Begrenzung der Anfragen pro Sekunde und IP-Adresse, um Missbrauch zu erschweren.
Reverse Proxy
Server, der Anfragen entgegennimmt und an die eigentlichen Programme weiterreicht (hier: nginx).
Umgebungsvariable / .env
Einstellungen, die von außen in ein Programm gegeben werden. Die Datei .env sammelt sie; sie enthält Passwörter und wird nie ins Repository eingecheckt.
