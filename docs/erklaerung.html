1. Was macht die Anwendung?

Die Website zeigt eine Liste von rund 4.000 Pflege- und Beratungsstellen in Deutschland. Man kann die Liste durchsuchen (Name, Ort, PLZ), nach Bundesland und Angebotsart filtern und beliebig viele Stellen per Checkbox auswählen. Ein Klick auf „E-Mail an Auswahl senden“ öffnet das eigene Mailprogramm (Outlook, Apple Mail …) mit allen gewählten Adressen bereits eingetragen.

Warum öffnet sich das eigene Mailprogramm statt dass der Server die Mail verschickt? Weil der Server dann keine Mail-Zugangsdaten braucht, keine E-Mails speichert und nicht als Spam-Schleuder missbraucht werden kann. Technisch ist das ein ganz normaler mailto:-Link – wie ein Link, der aber nicht eine Seite, sondern das Mailprogramm öffnet.

Außerdem gibt es eine Login-Pflicht: Niemand sieht die Liste, ohne sich vorher angemeldet zu haben.

2. Die Bausteine im Überblick

Die Anwendung besteht aus mehreren Programmen, die zusammenarbeiten. Jedes läuft in einem eigenen Container (siehe Glossar) auf ein und demselben Server:

Internet (Browser der Nutzer:innen) │ verschlüsselt (https, Port 443) ▼ ┌─────────────────────────────────────────────────────────┐ │ Ubuntu-Server │ │ │ │ ┌───────────┐ ┌──────────────────────────┐ │ │ │ nginx │ ───────► │ App (FastAPI / Python) │ │ │ │ "Türsteher"│ │ + Datenbank im RAM │ │ │ └───────────┘ └──────────────────────────┘ │ │ │ │ │ │ /idp/… ┌──────────────┐ ┌──────────┐ │ │ └──────────────► │ Keycloak │─►│ Postgres │ │ │ │ (Login) │ │ (für KC) │ │ │ └──────────────┘ └──────────┘ │ │ │ │ internes Docker-Netzwerk – von außen nicht erreichbar │ └─────────────────────────────────────────────────────────┘
BausteinWas er tutWarum genau dieser?
nginx Der einzige Baustein, der aus dem Internet erreichbar ist. Entschlüsselt HTTPS, leitet Anfragen an die App bzw. an Keycloak weiter, bremst zu viele Anfragen pro Sekunde aus (Rate-Limiting). Weltweit bewährter Standard-„Türsteher“. Alles Sicherheitsrelevante an der Außengrenze passiert an genau einer Stelle.
App (Python, FastAPI) Liefert die Webseite aus und beantwortet die Datenabfragen (/api/centers). Lädt beim Start die CSV-Datei in eine kleine Datenbank im Arbeitsspeicher. Python ist einsteigerfreundlich; FastAPI ist klein, schnell und erzeugt die API-Dokumentation automatisch (/api/docs).
Keycloak Übernimmt den kompletten Login: Benutzerkonten, Passwörter, Passwort-vergessen, Schutz vor Rate-Angriffen. Login selbst zu programmieren ist fehleranfällig. Keycloak ist eine Open-Source-Standardlösung, die genau das seit Jahren macht.
Postgres (nur für Keycloak) Speichert Keycloaks Benutzerkonten dauerhaft auf der Festplatte. Ohne echte Datenbank würde Keycloak alle Konten bei jedem Neustart vergessen.
Warum liegt die Datenbank der App „nur im Arbeitsspeicher“? Die Stellen-Daten ändern sich nicht durch die Nutzer:innen. Die CSV-Datei im Repository ist die „Wahrheit“; beim Start wird sie in eine SQLite-Datenbank im RAM geladen. Vorteil: kein Datenbank-Server nötig, trotzdem echtes SQL zum Filtern/Suchen. Startet der Container neu, wird einfach alles frisch geladen – es kann nichts verloren gehen.

3. Was passiert bei einem Seitenaufruf?

  1. Du tippst https://pflege-finder.example.org ein. Die Anfrage landet bei nginx, der die Verschlüsselung aufmacht.
  2. nginx reicht die Anfrage intern an die App weiter.
  3. Die App prüft: Bist du eingeloggt? (Dafür schaut sie in ein signiertes Cookie.) Falls nein → Weiterleitung zu /auth/login → weiter zu Keycloak.
  4. Du meldest dich bei Keycloak an. Keycloak schickt dich mit einem Einmal-Code zurück zur App (/auth/callback).
  5. Die App tauscht diesen Code direkt (Server zu Server, im internen Netz) gegen deine Benutzerinfos ein und merkt sich „eingeloggt“ im Cookie.
  6. Jetzt bekommst du die Seite. Das JavaScript im Browser lädt die Liste über /api/centers?… nach, du filterst, wählst aus, klickst auf „E-Mail senden“ → mailto: öffnet dein Mailprogramm.
Warum zwei verschiedene Adressen für Keycloak (OIDC_ISSUER und OIDC_ISSUER_INTERNAL)? Dein Browser erreicht Keycloak nur über die öffentliche Adresse (https://…/idp/). Die App dagegen spricht mit Keycloak direkt im Container-Netz (http://keycloak:8080/…) – schneller und ohne Umweg über nginx. Beides zeigt auf dasselbe Keycloak, nur über unterschiedliche „Türen“.

5. Sicherheit – einfach erklärt

HTTPS

Alles zwischen Browser und Server ist verschlüsselt. Unverschlüsselte Aufrufe (http://) werden automatisch auf https:// umgeleitet.

Login über Keycloak – „sicher von Haus aus“

Die Login-Pflicht ist standardmäßig an. Fehlen die Keycloak-Zugangsdaten, startet die App absichtlich gar nicht („Fail-fast“) – lieber ein sichtbarer Fehler als eine versehentlich offene Website.

Sicherheits-Header

Jede Antwort enthält Anweisungen an den Browser, z. B. „führe nur Skripte von dieser Seite aus“ (Content-Security-Policy) oder „zeige mich nicht in fremden Frames an“. Das schützt vor eingeschleustem Fremdcode.

Container-Härtung

  • Die App läuft nicht als Administrator (non-root) im Container.
  • Das Dateisystem ist schreibgeschützt; nur /tmp ist beschreibbar.
  • CPU und RAM sind begrenzt – ein Fehler kann nicht den ganzen Server lahmlegen.
  • Nur nginx hat offene Ports nach außen; App und Keycloak sind nur intern erreichbar.

Rate-Limiting & Begrenzung

nginx erlaubt pro IP nur ~10 Anfragen/Sekunde; die API liefert maximal 500 Einträge pro Anfrage. Niemand kann die ganze Adressliste „auf einen Schlag“ absaugen.

Keine Geheimnisse im Code

Passwörter und Schlüssel stehen ausschließlich in der lokalen .env-Datei, die per .gitignore vom Repository ausgeschlossen ist.

7. Session-Cookies & Co. – einfach erklärt

Das Grundproblem: HTTP ist vergesslich

Jede Anfrage an den Server ist für sich allein – der Server weiß beim zweiten Klick nicht mehr, dass du dich beim ersten eingeloggt hast. Damit das trotzdem funktioniert, gibt der Server dem Browser ein Cookie: ein kleines Stück Text, das der Browser bei jeder weiteren Anfrage an dieselbe Website automatisch mitschickt.

Was steht in unserem Cookie?

Das Cookie heißt session und enthält ein kleines JSON-Objekt:

{
  "user": { "sub": "3f1c…", "email": "demo@example.org", "name": "Demo Nutzer" },
  "id_token": "eyJhbGciOi…"      // für den Logout bei Keycloak
}

Dieser Inhalt wird Base64-kodiert und signiert – nicht verschlüsselt. Das heißt: Man kann ihn theoretisch lesen (es stehen auch keine Geheimnisse drin), aber man kann ihn nicht verändern, ohne dass die Signatur ungültig wird.

Was ist eine Signatur und wozu der SECRET_KEY? Der Server berechnet aus Cookie-Inhalt + SECRET_KEY eine Prüfsumme (HMAC) und hängt sie an. Bei jeder Anfrage rechnet er sie neu und vergleicht. Wer den Inhalt manipuliert (z. B. "email": "admin@…"), hat die passende Prüfsumme nicht – das Cookie wird verworfen, man gilt als nicht eingeloggt. Deshalb muss der SECRET_KEY geheim, lang und zufällig sein und darf kein Platzhalter wie change-me bleiben: Wer ihn kennt, könnte sich jedes beliebige Cookie selbst ausstellen.

Die Schutz-Flags am Cookie

FlagBedeutungSchützt vor
HttpOnlyJavaScript im Browser darf das Cookie nicht lesen.Diebstahl des Cookies durch eingeschleustes Skript (XSS).
SecureWird nur über HTTPS gesendet (im Produktivmodus aktiv).Mitlesen im unverschlüsselten WLAN.
SameSite=laxWird bei Anfragen, die eine fremde Seite auslöst, meist nicht mitgeschickt.„Cross-Site Request Forgery“ – fremde Seiten, die in deinem Namen Aktionen auslösen.
Max-Age=28800Läuft nach 8 Stunden automatisch ab.Ewig gültige Logins auf fremden Rechnern.

Warum kein serverseitiger Session-Speicher?

Viele Anwendungen speichern nur eine zufällige ID im Cookie und den Rest in einer Datenbank (Redis o. ä.). Hier liegt alles im Cookie. Vorteil: Die App braucht keinen zusätzlichen Speicher, bleibt zustandslos und ein Neustart loggt niemanden aus. Nachteil: Eine einzelne Sitzung lässt sich nicht serverseitig „abschießen“ – nur über Keycloak (dort „Sessions beenden“) oder durch Ändern des SECRET_KEY, was alle Nutzer:innen gleichzeitig ausloggt.

Drei Dinge, die oft verwechselt werden

Session-Cookie (unseres)
Vom App-Server gesetzt, gilt für pflege-finder.example.org. Sagt der App: „Diese Person ist eingeloggt.“
Keycloak-Cookies
Von Keycloak unter /idp/… gesetzt. Sagen Keycloak: „Diese Person hat sich schon angemeldet“ – deshalb klappt ein zweiter Login ohne erneute Passworteingabe (Single Sign-On).
Tokens (ID-Token, Access-Token)
Signierte Datenpakete, die Keycloak der App gibt (Schritt 7 im Flow-Chart). Sie landen nie im Browser-JavaScript; die App liest daraus Name/E-Mail und merkt sich nur den id_token für den sauberen Logout.

8. Wie genau die Datenbank eingebunden ist

Die Idee in einem Satz

Die CSV-Datei im Repository ist die Wahrheit; beim Start wird sie in eine SQLite-Datenbank im Arbeitsspeicher geladen, und die API fragt diese per SQL ab.

app/data/pflegestellen.csv (versioniert in Git, ~4.090 Zeilen) │ │ beim Containerstart (lifespan in main.py) ▼ seed.py: CSV lesen ─► Zeile für Zeile Center(...)-Objekte ─► db.commit() │ ▼ SQLite ":memory:" ─ Tabelle "centers" mit Indizes auf name, plz, ort, bundesland ▲ │ pro Anfrage: Session öffnen → SELECT … → Session schließen │ routers/centers.py (/api/centers, /api/bundeslaender)

Die vier beteiligten Dateien

DateiAufgabeKernstück
database.py Erzeugt die Verbindung (Engine) und die Session-Fabrik. create_engine("sqlite://", poolclass=StaticPool, connect_args={"check_same_thread": False})
models.py Beschreibt die Tabelle als Python-Klasse (ORM). class Center(Base): id, name, plz, ort, bundesland, email, …, pflegeberatung: bool, …
seed.py Liest die CSV und befüllt die Tabelle. csv.DictReader(f, delimiter=";") → db.add(Center(...))
routers/centers.py Baut aus den Filter-Parametern eine SQL-Abfrage. select(Center).where(…).order_by(…).offset(…).limit(…)

Warum diese beiden merkwürdigen Einstellungen?

StaticPool Eine SQLite-Datenbank „im Speicher“ gehört normalerweise zu genau einer Verbindung – jede neue Verbindung bekäme eine neue, leere Datenbank. StaticPool sorgt dafür, dass alle Anfragen dieselbe eine Verbindung wiederverwenden und damit dieselben Daten sehen.
check_same_thread=False SQLite erlaubt eine Verbindung standardmäßig nur in dem Thread, der sie geöffnet hat. FastAPI bearbeitet Anfragen aber in verschiedenen Threads. Die Einstellung hebt diese Prüfung auf – unproblematisch, weil wir nur lesen.

Was passiert bei einer Anfrage wie /api/centers?bundesland=SN&search=Dresden?

  1. FastAPI ruft get_db() auf → eine neue Session (Arbeitskontext) wird geöffnet.
  2. Die Abfrage wird Stück für Stück zusammengebaut: 
    stmt = select(Center)
stmt = stmt.where(Center.bundesland == "SN")
stmt = stmt.where(Center.name.ilike("%Dresden%") | Center.ort.ilike("%Dresden%") | Center.plz.ilike("%Dresden%"))
  3. Zwei SQL-Befehle gehen an SQLite: einmal SELECT COUNT(*) für „x Treffer insgesamt“, einmal die eigentliche Liste mit ORDER BY ort, name LIMIT 200 OFFSET 0.
  4. Die Ergebniszeilen werden zu Center-Objekten, dann per Pydantic (CenterOut) in JSON umgewandelt.
  5. Die Session wird geschlossen (finally: db.close()) – auch bei Fehlern.
Warum SQL und nicht einfach eine Python-Liste filtern? Mit ~4.000 Einträgen würde eine Liste auch funktionieren. Aber: SQLAlchemy abstrahiert die Datenbank. Soll später ein Admin-Bereich Stellen bearbeiten können, wechselt man in database.py nur die URL auf postgresql://…, ergänzt einen Postgres-Container – und models.py, routers/ bleiben unverändert.

Mehrere Worker = mehrere Datenbanken

Gunicorn startet 2 Worker-Prozesse. Jeder lädt beim Start seine eigene Kopie der CSV in seinen eigenen Arbeitsspeicher. Das ist unkritisch, weil beide exakt dieselben Daten aus derselben Datei haben und nichts schreiben – es wäre aber der erste Grund, auf eine gemeinsame Datenbank zu wechseln, sobald Daten geändert werden sollen.

Die Keycloak-Datenbank ist eine andere

Nicht verwechseln: Der keycloak-db-Container (Postgres) gehört nur Keycloak und speichert Benutzerkonten dauerhaft auf einem Docker-Volume. Die App greift darauf nie zu.

9. Wie die GitHub Action funktioniert

Was ist eine GitHub Action?

GitHub kann bei bestimmten Ereignissen (z. B. „jemand hat auf main gepusht“) automatisch Befehle auf einem Leih-Rechner („Runner“) ausführen. Was genau passieren soll, steht in einer YAML-Datei unter .github/workflows/. Unsere heißt deploy.yml.

Wann startet sie?

on:
  push:
    branches: [main]   # jeder Merge/Push auf main
  pull_request:        # jeder PR – aber nur der Test-Job (siehe unten)

Die drei Jobs und ihre Reihenfolge

Ereignispush auf main oder Pull Request
▼
Job 1: testPython 3.12 einrichten · pip install · ruff check . · pytest -q
▼
Tests grün und Ereignis = push auf main?nein → Ende (PRs stoppen hier bewusst)
▼ja
Job 2: build-and-pushDocker-Image aus app/Dockerfile bauen · bei GHCR anmelden · hochladen als :latest und :sha-<commit>
▼needs: build-and-push
Job 3: deployPer SSH auf den Ubuntu-Server · git reset --hard origin/main · IMAGE_TAG=sha-… in .env schreiben · docker compose pull && up -d
▼
Health-Checkbis zu 12× alle 5 s curl https://localhost/healthz · bei Misserfolg: docker compose logs ausgeben, Job rot

Die wichtigsten Zeilen, erklärt

AuszugWas es bedeutet
needs: testJob 2 wartet auf Job 1 und läuft nur, wenn der erfolgreich war. So wird nie ungetesteter Code gebaut.
if: github.event_name == 'push'Für Pull Requests wird nur getestet, nicht gebaut oder deployt – ein PR darf den Server nicht anfassen.
permissions: packages: writeDer Job darf Images in die GitHub Container Registry (GHCR) hochladen – und sonst nichts.
secrets.GITHUB_TOKENVon GitHub automatisch erzeugter, kurzlebiger Schlüssel für diesen einen Lauf. Kein manuell gepflegtes Passwort nötig.
secrets.SSH_HOST / SSH_USER / SSH_PRIVATE_KEYZugangsdaten zum Server, in GitHub unter Settings → Secrets hinterlegt. Sie erscheinen nie im Code oder in Logs.
cache-from/cache-to: type=ghaDocker-Schichten werden zwischen Läufen zwischengespeichert – unveränderte Teile (z. B. installierte Pakete) werden nicht jedes Mal neu gebaut.
type=sha (metadata-action)Erzeugt den Tag sha-1a2b3c4 aus dem Commit. Damit ist jedes Image eindeutig einem Code-Stand zuzuordnen.
sed -i '/^IMAGE_TAG=/d' .env; echo "IMAGE_TAG=…" >> .envTrägt auf dem Server den exakten Tag ein, den docker-compose.yml über ${IMAGE_TAG} liest. Rollback = alten Tag eintragen, docker compose up -d.
git checkout -f main / reset --hardHolt docker-compose.yml, nginx-Config usw. auf den Server. Die .env ist nicht in Git und bleibt unberührt.
Warum wird das Image auf GitHub gebaut und nicht auf dem Server? Das Image entsteht einmal, nach bestandenen Tests, und der Server führt exakt dieses aus. Würde der Server selbst bauen, könnten Unterschiede (andere Paketversionen, halbfertiger Build bei Abbruch) zu „bei mir geht's aber“-Problemen führen.
Was passiert, wenn der Health-Check rot wird? Der neue Container läuft dann bereits – der Workflow macht kein automatisches Rollback. Er gibt docker compose ps und die letzten Logs aus, damit man die Ursache sieht. Manueller Rollback: in der Server-.env den vorherigen IMAGE_TAG eintragen und docker compose up -d.

Zwei weitere, kleinere Automatiken

  • .github/dependabot.yml – kein Workflow, sondern eine Konfiguration: GitHub prüft wöchentlich Python-Pakete, Docker-Images und Actions auf neue Versionen und öffnet Pull Requests. Diese laufen dann automatisch durch den test-Job.
  • dependency-graph.yml – meldet alle erkannten Abhängigkeiten (auch Docker-Images) an GitHubs Dependency Graph, damit Sicherheitslücken in Paketen als Alerts sichtbar werden.

11. Glossar

API
Eine Schnittstelle, über die Programme (hier: das JavaScript im Browser) Daten abfragen – statt einer fertigen Webseite kommt rohes JSON zurück.
Container / Docker
Ein Container ist ein abgeschottetes Mini-System, in dem genau ein Programm mit allem läuft, was es braucht. Docker baut und startet diese Container. Docker Compose beschreibt mehrere Container und ihr gemeinsames Netzwerk in einer Datei.
CI/CD
„Continuous Integration / Continuous Deployment“: Code wird bei jeder Änderung automatisch geprüft (CI) und ausgerollt (CD). Hier über GitHub Actions.
Cookie (Session)
Kleines Datenpaket, das der Browser bei jeder Anfrage mitschickt. Die App speichert darin „eingeloggt als …“ – signiert mit dem SECRET_KEY, damit es niemand fälschen kann.
CSV
Einfache Textdatei mit Tabellendaten, Spalten durch ; getrennt.
Fail-fast
Prinzip: Bei fehlerhafter Konfiguration sofort und sichtbar abbrechen, statt „irgendwie“ weiterzulaufen.
HTTPS / TLS
Verschlüsselte Verbindung zwischen Browser und Server (das Schloss-Symbol).
Lint (ruff)
Automatische Code-Prüfung auf Stil- und häufige Logikfehler, noch bevor etwas läuft.
Middleware
Code, der vor jeder Anfrage läuft – wie ein Türsteher, der prüft, ob du rein darfst, bevor die eigentliche Seite angefasst wird.
OIDC (OpenID Connect)
Standardverfahren für „Login über einen anderen Dienst“ – dasselbe Prinzip wie „Mit Google anmelden“, nur mit Keycloak.
Rate-Limiting
Begrenzung der Anfragen pro Sekunde und IP-Adresse, um Missbrauch zu erschweren.
Reverse Proxy
Server, der Anfragen entgegennimmt und an die eigentlichen Programme weiterreicht (hier: nginx).
Umgebungsvariable / .env
Einstellungen, die von außen in ein Programm gegeben werden. Die Datei .env sammelt sie; sie enthält Passwörter und wird nie ins Repository eingecheckt.
